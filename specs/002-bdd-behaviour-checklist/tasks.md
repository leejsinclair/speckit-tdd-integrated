# Tasks: BDD Behaviour Checklist

**Input**: Design documents from `/specs/002-bdd-behaviour-checklist/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md

**Tests**: Included and mandatory. Constitution Principle IV requires every executable
component to be built test-first, as in 001: each rule and each changed behaviour of the
check script gets a failing fixture test before it is implemented. Markdown wrappers, rules
and templates are prompts, so they get structural tests written first plus installation
checks and story runs (plan.md, Constitution Check IV).

**Organization**: Tasks are grouped by user story so each story can be implemented and
tested on its own.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (US1 to US5)
- Every description names the file or directory it changes

## Path Conventions

- Single project, as in 001. Both manifests sit at the repository root
- Extension files: `commands/`, `templates/`, `scripts/python/`
- Preset files: `preset/commands/`, `preset/templates/`
- Development and evaluation material: `tests/`, `examples/`, `docs/`
- `<repo>` is this repository. `<tmp>` is a throwaway directory outside it. Never install
  into this repository's own `.specify/`
- The check script is run as `python3 -B scripts/python/tdd_check.py`. The test suite is
  run as `python3 -B -m unittest discover -s tests`
- "Older feature" means a feature whose Verification Plan has no `### Behaviour checklist`
  sub-heading and which has no `tests/behaviour-checklist.md` (research D5)

## Conventions for every test task

- Write the tests, run the suite, and confirm the new tests fail for the intended reason
  (the behaviour is missing, not an import or fixture error) before starting the
  implementation task that follows
- Commit each test task while its new tests fail, before any implementation of what they
  test. The commit message lists the failing tests and the failure reason as the run
  printed it. The implementation task that makes them pass is a later, separate commit
  whose message gives the passing run's summary line. Git history is this project's
  evidence of Red before Green, because the check script is not installed here. Never
  amend or squash these commits together: T063 replays them
- Tests drive the script as a subprocess through `tests/support.py` and assert exit code,
  standard output and standard error exactly, as
  [the check script changes](./contracts/check-cli-changes.md) and
  [the checklist contract](./contracts/behaviour-checklist.md) define them
- Fixtures are generated by `tests/fixtures/make_features.py` into
  `tests/fixtures/features/<case-name>/`; never edit a generated fixture by hand. A new
  fixture for a checklist case starts from `valid-minimal`, adds the
  `### Behaviour checklist` sub-heading to its `plan.md`, and writes
  `tests/behaviour-checklist.md`
- No existing fixture is changed, and no existing assertion is changed except two evidence
  paths: the shared helper's, named in T006, and the compliant-example test's, named in
  T047
- A task that the parallel lists below place after a test task starts only once that test
  task's failing commit exists, even when the two touch different files
- The code must run on Python 3.9: no `match`, no `X | Y` type unions at runtime, no
  `tomllib`

## Implementation Strategy

### MVP First (User Stories 1 and 2)

1. Phase 1: Setup
2. Phase 2: Foundational, stopping at T003 or T004 if needed
3. Phase 3: User Story 1
4. Phase 4: User Story 2
5. **Stop and validate** with T029: the checklist is written at planning and checked, and
   implementation cannot start while it fails

User Story 1 alone produces a checklist that nothing checks, which is the "document the
agent writes and then forgets" that User Story 2 exists to prevent. The smallest increment
worth releasing is User Stories 1 and 2 together.

### Incremental Delivery

1. Setup and Foundational: approvals, Spec Kit 1.1.3, the 0.1.0 guard, evidence location,
   parser
2. User Stories 1 and 2: the checklist written and checked (MVP)
3. User Story 3: the side-by-side review view and review guidance
4. User Story 4: items fixed at the baseline, drift detected, status per item
5. User Story 5: documentation, examples and story 08
6. Polish: performance, Python 3.9, upgrade path, release, replay

### Parallel Team Strategy

All rule logic is one module, so parallel work is limited. One developer can take the
script tasks in order while a second writes fixtures, the template, rules sections,
wrappers, examples and documentation.
