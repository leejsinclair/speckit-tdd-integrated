# Tasks: Verification Only Where It Is Possible

**Input**: Design documents from `/specs/003-no-tooling-manual-verification/`

**Prerequisites**: plan.md, spec.md, research.md, data-model.md, contracts/, quickstart.md

**Tests**: Included and mandatory. Constitution Principle IV requires every executable
component to be built test-first, as in 001 and 002: each rule and each changed behaviour of
the check script gets a failing fixture test before it is implemented. Markdown wrappers,
rules and templates are prompts, so they get structural tests written first plus
installation checks and story runs (plan.md, Constitution Check IV).

**Organization**: Tasks are grouped by user story so each story can be implemented and
tested on its own.

## Format: `[ID] [P?] [Story] Description`

- **[P]**: Can run in parallel (different files, no dependencies)
- **[Story]**: Which user story this task belongs to (US1 to US4)
- Every description names the file or directory it changes

## Path Conventions

- Single project, as in 001 and 002. Both manifests sit at the repository root
- Extension files: `commands/`, `templates/`, `scripts/python/`
- Preset files: `preset/commands/`, `preset/templates/`
- Development and evaluation material: `tests/`, `examples/`, `docs/`
- `<repo>` is this repository. `<tmp>` is a throwaway directory outside it. Never install
  into this repository's own `.specify/`
- The check script is run as `python3 -B scripts/python/tdd_check.py`. The test suite is
  run as `python3 -B -m unittest discover -s tests`
- "No-tooling mode" means a plan whose Verification commands table holds only a `None` row
  (research D1). "Standing deferral" is defined in data-model.md

## Conventions for every test task

- Write the tests, run the suite, and confirm the new tests fail for the intended reason
  (the behaviour is missing, not an import or fixture error) before starting the
  implementation task that follows
- Commit each test task while its new tests fail, before any implementation of what they
  test. The commit message lists the failing tests and the failure reason as the run
  printed it. The implementation task that makes them pass is a later, separate commit
  whose message gives the passing run's summary line. Git history is this project's
  evidence of Red before Green, because the check script is not installed here. Never
  amend or squash these commits together: T040 replays them
- Tests drive the script as a subprocess through `tests/support.py` and assert exit code,
  standard output and standard error exactly, as
  [the check script changes](./contracts/check-cli-changes.md) define them
- Fixtures are generated by `tests/fixtures/make_features.py` into
  `tests/fixtures/features/<case-name>/`; never edit a generated fixture by hand. A new
  fixture starts from `valid-minimal` or `checklist-valid` and changes only what its case
  needs
- No existing fixture is changed, and no existing assertion is changed. If one fails, the
  change has broken 0.2.0 behaviour (SC-006): stop and return the design to the developer
- A fixture named by more than one task is defined once, by the first task that names it, and
  reused by the others
- A task that the parallel lists below place after a test task starts only once that test
  task's failing commit exists, even when the two touch different files
- The code must run on Python 3.9: no `match`, no `X | Y` type unions at runtime, no
  `tomllib`
- Commit messages end with the two attribution lines the session requires

## Implementation Strategy

### MVP First (User Story 1)

1. Phase 1: Setup
2. Phase 2: Foundational, stopping at T003 if an approval is declined
3. Phase 3: User Story 1
4. **Stop and validate**: a project with no test tooling gets through the script's checks
   with nothing refused. The wrappers (Phase 6) are needed before an agent does it

User Story 1 alone already removes the largest block: a new project can use the process.
The smallest increment worth releasing is User Stories 1 and 2, because without deferral
an unreachable service still holds tasks.

### Incremental Delivery

1. Setup and Foundational: approval, 0.2.0 guard, parsing
2. User Story 1: no test tooling (MVP)
3. User Story 2: deferred obligations
4. User Story 3: manual verification
5. User Story 4: wrappers, rules, documentation, examples, story 09
6. Polish: whole-suite checks, installation, agent runs, replay

### Parallel Team Strategy

All rule logic is one file, so parallel work is limited. One developer can take the script
tasks in order while a second writes fixtures, wrappers, rules, examples and documentation.
